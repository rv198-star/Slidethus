# M2.1 Review Round A — Open Issue Mining

## Scope

Review M2.1 Ingestion Core without scores. The review inspected parser contracts, format admission, source identity, cache immutability, metadata policy, locators, source-risk coverage, crash recovery, Schema references, CLI behavior and MVP1 regression. It did not evaluate M2.2 multi-format adapters, research runtime or the Evidence Engine.

## Findings

### Major — cache reuse silently ignored policy and parsing-limit changes

- Location: `SourceIngestionService.ingest` reusable-snapshot path.
- Problem: an unchanged file returned the old Source Ledger record immediately. A caller changing `allowed_use`, confidentiality or title received `changed=false`; a changed `max_chunk_chars` also reused the old Chunk set. This could retain an unsafe permission and make parser behavior disagree with the requested contract.
- Root fix: metadata defaults now inherit the existing record, explicit policy changes create a new Source Ledger version while reusing the verified snapshot, and parser limits are part of both Ledger lineage and cache-reuse eligibility. Changed limits create a new snapshot.
- Verification: policy update, no-op repeat and limit-change tests assert Ledger versions, snapshot identity and preserved metadata.

### Major — stable Source IDs could be rebound or aliased

- Location: source ID resolution.
- Problem: an explicit existing `source_id` could replace the record with another file, and an already inventoried path could be registered under a second ID.
- Root fix: source IDs are one-to-one with canonical user-file paths. Rebinding and path aliasing now fail before parsing or Ledger publication.
- Verification: both collision directions are covered by deterministic tests.

### Major — immutable cache publication had a check-then-replace race

- Location: source snapshot write path.
- Problem: `exists()` followed by atomic replace allowed two writers to publish different snapshot bytes at the same input key, because `created_at` is not part of the key. The later writer could replace the winner while another Ledger transaction referenced its hash.
- Root fix: immutable files now use a fully written and fsynced temporary file followed by create-if-absent hard-link publication. Existing destinations are never replaced; the loser validates and reuses the winner.
- Verification: create-if-absent behavior and orphan-snapshot recovery are covered; Artifact Runtime optimistic locking still arbitrates Ledger publication.

### Major — parsed bytes, size and source hash were not one atomic observation

- Location: `TextSourceParser.parse` and `fingerprint_source`.
- Problem: parser text came from `read_bytes()`, while size and SHA-256 were read separately from the path. A changing file could produce Chunks for one byte sequence and lineage for another.
- Root fix: the parser derives text, size and source hash from the same byte payload and rechecks the size limit after reading. Reuse fingerprints also hash one captured payload and are confirmed before returning a cached result.
- Verification: all snapshot content/hash invariants and mutation-sensitive reuse paths pass.

### Major — format admission was broader and less reliable than the claimed adapter set

- Location: deterministic format detection and `TextSourceParser.supports`.
- Problem: UTF-16 detection was unreachable because NUL rejection ran before BOM handling. Conversely, a UTF-8 CSV could be admitted as generic text even though CSV belongs to M2.2.
- Root fix: BOM detection precedes generic binary rejection; CSV/TSV are identified as separate families; the text adapter admits only Markdown, TXT and extensionless plain text. Recognized formats without an adapter fail explicitly.
- Verification: UTF-16 TXT succeeds and CSV remains unsupported.

### Major — locator precision and source-risk coverage were incomplete

- Location: long-line splitting and risk scanning.
- Problem: several fragments from one oversized line received the same line locator, so downstream evidence could not distinguish them. Risk scanning inspected body text but not Markdown headings, allowing instruction-like headings to avoid source-risk records.
- Root fix: same-line fragments now include character ranges in their locators and metadata; risk detection scans both title metadata and body text.
- Verification: unique character-range locators and heading-only prompt-injection wording are covered.

### Minor — snapshot references were not fully self-authenticating

- Location: source snapshot validation.
- Problem: validation checked file and Chunk hashes but did not recompute the input-key filename, derive Chunk IDs from source/ordinal/hash, enforce source-scoped risk ID order or compare snapshot limits with Ledger lineage.
- Root fix: all four invariants are now checked during workspace validation.
- Verification: tampered snapshots fail with `invalid_source_snapshot`; the complete workspace and packaged Schema mirror remain valid.

## Regression checks

- M1 journaled Artifact Runtime and optimistic locking remain the only writer for Source Ledger facts.
- Existing M0/MVP Source Ledger records without `ingestion` remain valid; new production-parsed records require a snapshot.
- MVP1 still reaches G9 with independent preview fixtures and still fails G8 honestly when previews are unavailable.
- No provider SDK, network call or new production dependency was added.
- Source-preserved material was not modified.

## Result

Critical findings: 0. Major findings: 6, all fixed. Minor findings: 1, fixed. Round B proceeds after full tests, Schema validation, package audit and diff review.
