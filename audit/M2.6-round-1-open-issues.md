# M2.6 Review Round A — Open Issue Mining

## Scope

This review evaluated the integrated M2 application boundary without scores. It inspected application ordering, current Gate semantics, provider/disclosure policy, explicit degradation, high-risk Source isolation, requested/current resource budgets, application-report lineage, existing-planning revalidation, targeted Research actions, CLI behavior, idempotency and M2.1–M2.5 regression.

Vendor-specific online adapters, M3 artifact generation, final rendering and the repository-wide M2 Exit Gate were excluded because they are explicit M2.6 non-goals.

## Findings

### Critical

None.

### Major — independent Production services had no governed application order

- Problem: M2.1–M2.5 could be called independently, but there was no single boundary proving that Source, Research, Evidence, Gap and Gate operations were invoked in the correct order with one capability decision.
- Root fix: `M2ApplicationService` now owns the integrated sequence while delegating every semantic write to the existing services and Artifact Runtime.
- Verification: local D3, explicit degraded, provider-backed D0, existing-planning and rework end-to-end tests use the same application entry.

### Major — Research materialization invalidated G1 but application attempted G2 directly

- Problem: a completed orientation or targeted Research Run materializes new Web Sources. Source Ledger versioning correctly rewinds the workflow below G1; attempting G2 immediately produced an invalid `BRIEF_READY → EVIDENCE_READY` transition.
- Root fix: every Research materialization path re-establishes current G1 before G2, then revalidates G3/G4/G5A where applicable.
- Verification: both orientation and current-outline targeted provider tests pass after Web Source insertion.

### Major — provider capability could have been confused with permission to disclose

- Problem: injecting a ResearchProvider could otherwise imply permission to transmit Brief/Outline query text.
- Root fix: provider availability and `approve_external_disclosure` are independent decisions. Actual provider execution requires both; CLI ships no provider.
- Verification: provider call count remains zero without approval and becomes positive only in the approved path.

### Major — missing external research needed explicit D5/D3 semantics

- Problem: a convenience orchestrator could silently use local materials when the Brief required external research, including freshness-constrained work.
- Root fix: missing provider/disclosure defaults to D5. D3 requires explicit `allow_research_degraded` and is refused when the Brief has a freshness requirement. The Evidence cycle records a real waiver reason and no fake Research Result.
- Verification: default block, explicit offline degradation and freshness-constrained rejection are separate tests.

### Major — high-risk Source instructions could have entered automatic Evidence promotion

- Problem: Source ingestion correctly recorded prompt-injection/active-content risks, but an integrated loop could promote every parsed Chunk to Evidence by default.
- Root fix: Sources with high-severity findings remain inventoried but are excluded from automatic Evidence unless the caller explicitly enables the override. No Source instruction is executed.
- Verification: the default path blocks when the excluded Source is the only citation basis; explicit override is recorded in the Application Report.

### Major — application budgets could be bypassed by existing inventory or file growth

- Problem: checking only requested Source count/bytes would ignore Sources already in the Ledger. A file could also change after preflight, making the report fingerprint and total budget disagree with ingested bytes.
- Root fix: the application checks unique requested inputs, current Source Ledger count/bytes, per-Source parser limits and Research limits. Post-ingestion fingerprints are rebound to the captured Source bytes and any change is reported.
- Verification: requested total-byte and existing inventory-count tests fail before Evidence/provider work.

### Major — citation-required G2 admitted inference-only ledgers

- Problem: G2 previously required only a non-empty Evidence Ledger. Source-less inference/assumption claims could satisfy `citation_required=true` despite having no usable Source reference.
- Root fix: G2 and user-material orientation completion require at least one usable `verified/provisional` source-backed claim. Inference remains representable but cannot satisfy citation readiness.
- Verification: a complete example rewritten to inference-only claims now fails G2 with the explicit reason.

### Major — Application Report lacked a bound Project State revision

- Problem: artifact refs alone did not prove the reported final phase or accepted Gate summaries. A syntactically valid, rehashed report could claim `COMPLETED` while the workspace remained at an earlier phase.
- Root fix: every report now binds a current/historical Project State revision and content hash. Validation compares final phase and the Gates required by that phase against the bound state.
- Verification: a forged report with recomputed report ID/filename but false final phase fails workspace validation.

### Major — report publication did not verify all references before success

- Problem: schema-valid report bytes could still contain an invalid Gap path, historical artifact ref or Project State relation.
- Root fix: report publication validates all references after create-if-absent; a newly created invalid report is removed before the application returns failure.
- Verification: tamper, historical-artifact and gap-reference validation paths are covered.

### Major — unchanged legacy research-cycle representation caused mature phase rollback

- Problem: existing valid cycles without the newer optional `run_ids=[]` field were semantically equivalent, but application normalization treated them as changed and rewrote Evidence, invalidating downstream planning/render phases.
- Root fix: user-material orientation completion compares normalized semantic values; missing and empty optional lineage arrays are equivalent, and notes alone never force a semantic rewrite.
- Verification: the mature example keeps its original phase and Outline bytes during M2 revalidation.

### Major — targeted Research execution was absent from the application action record

- Problem: Research Runs and Sources appeared in outputs, but the application action chain did not explicitly state whether targeted Research executed, was already complete, used user materials, or was blocked.
- Root fix: every targeted branch records a `targeted_research` action with stable status, detail and Run refs.
- Verification: provider-backed current-outline testing asserts a completed targeted action and multiple Research Runs.

### Minor — duplicate requested paths consumed Source-count budget

- Problem: repeated identical CLI `--source` values could trigger `max_sources` despite representing one Source.
- Root fix: canonical paths are deduplicated before count/byte preflight.

### Minor — runtime directory admitted unrelated entries silently

- Problem: only `*.json` reports were inspected; unrelated files/subdirectories in `.slidethus/m2/runs/` were ignored.
- Root fix: workspace validation reports every unexpected entry.

### Minor — capability/report/CLI documentation lagged implementation

- Problem: architecture, artifact, security, degradation, compatibility, Skill and README text did not describe disclosure approval, high-risk isolation, M2 Reports or `m2` commands.
- Root fix: ADR-0014 and all applicable docs now share the same boundary and non-goals.

## Regression evidence after fixes

- M2.1–M2.5 service contracts and their dedicated tests remain green.
- CLI continues to expose no online provider or credentials.
- Application reports are content-addressed, idempotent and historical-version aware.
- Existing Narrative/Outline/Specs are read/revalidated only; M2.6 never generates or edits M3 content.
- No network call occurs in unit tests.
- Source-preserved material was not modified.

## Result

- Critical findings: 0.
- Major findings: 11, all root-fixed.
- Minor findings: 3, all fixed.
- Waivers: none.

Round B may proceed only after the final Python 3.11/3.12 suites, package audit and documentation/diff review pass.
