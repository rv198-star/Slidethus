# M2.4 Review Round A — Open Issue Mining

## Scope

This review evaluated the deterministic Evidence Engine without scores. It inspected claim identity, Research Result materialization, Source/Evidence lineage, exact deduplication, stable IDs, authority/freshness/use-policy decisions, explicit conflict groups, semantic research-cycle completion, optimistic locking, workspace validation, G2 and CLI behavior.

Block-level Slide Spec binding and outline gap routing were excluded because they belong to M2.5. Vendor search adapters, Web-page fetching, LLM claim extraction and semantic-near-duplicate clustering remain explicit non-goals.

## Findings

### Critical

None.

### Major — claim normalization erased units and numerical operators

- Problem: the first exact-dedupe normalizer removed all Unicode punctuation. This made materially different claims such as `10%` versus `10`, `1.5` versus `15`, `A/B` versus `AB`, or `-5` versus `5` eligible for the same claim key.
- Root fix: normalization now removes presentation punctuation conservatively while preserving percent/unit symbols, ratios, decimal punctuation, unary signs and numeric ranges. Typographic dashes between words still normalize to spaces.
- Verification: dedicated unit/operator counterexamples produce different claim keys; typographic presentation variants remain stable duplicates.

### Major — repeated research of one canonical URL replaced unrelated historical result lineage

- Problem: materializing a later Research Run for a URL rebuilt the Web Source Snapshot from only that Run. Results from another provider or cycle at the same URL disappeared from the current source, invalidating otherwise independent Evidence and making cycle lineage fragile.
- Root fix: materializer-owned Web Sources recover existing result records and merge them by stable `RSLT-*`. A refreshed identical result replaces its own record; different results/runs remain distinct Chunks. Current-run candidates are returned without re-adjudicating unrelated historical results.
- Verification: two provider versions for one cycle share `SRC-001`, retain two source Chunks, preserve both Run IDs and aggregate query count.

### Major — semantic cycle completion was not idempotent and under-counted multiple Runs

- Problem: repeating cycle completion always wrote a new Evidence Ledger version. When multiple Runs belonged to one cycle, `query_count` was overwritten with the latest Run's task count rather than the total lineage.
- Root fix: cycle completion verifies every referenced Run, aggregates task counts, unions Run/source IDs and performs no Artifact write when the semantic cycle is unchanged.
- Verification: repeated completion leaves the Evidence Ledger version unchanged; a two-provider cycle records two Runs and two queries.

### Major — candidate references were not self-authenticating lineage

- Problem: Production claims persisted only `candidate_refs` IDs plus aggregate source refs/stances. If one of several duplicate-source candidates became stale, the Engine could not identify which candidate remained valid and cleared all candidate references. Conflict/freshness decisions could not be reconstructed from current candidate facts.
- Root fix: Production claims now persist bounded `candidate_bindings` containing source/locator/chunk/hash, origin, Research lineage, conflict key/stance and freshness. Candidate IDs are recomputed during validation. Reconciliation filters only invalid bindings, rebuilds refs/stances and re-adjudicates every Production claim.
- Verification: invalidating one of two duplicate sources preserves the other binding and verified claim; tampered bindings are rejected transactionally.

### Major — existing claims did not automatically re-evaluate a stricter freshness policy

- Problem: an existing untouched claim kept its old freshness decision unless one of its Source refs became invalid or the same claim was submitted again.
- Root fix: binding-backed reconciliation re-runs authority, freshness and use-policy decisions for every Production claim on each adjudication pass.
- Verification: introducing a cutoff while adjudicating another claim changes the untouched old claim to stale/qualified.

### Major — Source/Evidence optimistic locking used a split body/version observation

- Problem: Services could read an artifact body, perform work, then obtain the current version immediately before write. A concurrent writer between those reads could make an old body appear current and permit silent replacement.
- Root fix: Artifact Runtime exposes one locked `read_artifact_snapshot()` operation returning body and version from the same observation. Source Ingestion and Evidence Engine write against that captured version.
- Verification: injected concurrent Source and Evidence writers produce `ArtifactConflictError`; the winning writer's data remains intact.

### Major — Source changes initially made the workspace unrepairable instead of invalidating Evidence

- Problem: strict cross-reference validation originally made a Source update transaction fail whenever existing Production Evidence still pointed to the old Chunk. That prevented the upstream fact from changing and blocked the repair path.
- Root fix: Source writes are allowed, downstream Evidence is marked draft, stale bindings become validation warnings while G2 fails explicitly. Evidence reconciliation then downgrades or replaces claims and restores a valid approved ledger.
- Verification: changed source bytes commit, G2 reports invalidated lineage, old `EVD-*` becomes unsupported/do-not-use and the replacement claim receives a new stable ID.

### Major — incremental conflict facts did not initially propagate to prior claims

- Problem: adding an opposing candidate in a later run could mark only the new claim disputed, leaving the prior claim usable.
- Root fix: conflict groups are recomputed across current bindings and applied to every member. When opposing current support disappears, the group is released and remaining claims are re-adjudicated.
- Verification: incremental supports/opposes inputs block both claims; changing the opposing source releases the surviving claim and retires the invalid claim.

### Major — Web Source ownership could be silently overwritten

- Problem: canonical URL reuse without ingestion ownership checks could replace a Web Source created by another ingestion/fetch path with a provider summary.
- Root fix: Research materialization reuses only Sources owned by `research-result-materializer`; any other current Web Source at the canonical URL fails closed.
- Verification: an existing independently owned Web Source is preserved and materialization raises an explicit error.

### Minor — canonical URL identity admitted credentials and unstable presentation fragments

- Problem: raw provider URLs could carry user-info or fragment-only identity differences.
- Root fix: only HTTP(S) URLs without credentials are admitted; host/scheme/default port normalize and fragments are removed while query parameters remain.

### Minor — Production evidence fields were optional at Schema level for legacy compatibility

- Problem: M0/MVP examples require backward compatibility, so new adjudication fields cannot be globally required by JSON Schema alone.
- Root fix: cross-artifact validation requires claim key, candidate refs/bindings, authority/freshness/conflict and adjudication facts whenever `adjudication.engine=deterministic-evidence-engine`. Legacy manually curated claims remain valid.

### Minor — Research summary success could be mistaken for fetched Web evidence

- Problem: without explicit coverage metadata, a provider summary might be described as remote page text.
- Root fix: materialized Web Sources are always `partial`, Chunks carry `remote_body_fetched=false`, warnings/notes state the boundary, and their Evidence is at most provisional/qualified.

## Regression evidence

- M1 remains the only transactional writer for Source and Evidence Ledgers.
- M2.1–M2.3 Snapshot/Run/Cache lineage remains byte/hash validated.
- Research Result remains distinct from Source body and verified Evidence.
- Existing MinimalImpl examples remain Schema-compatible.
- No network client, command execution, macro, formula or embedded-object execution was introduced.

## Result

- Critical findings: 0.
- Major findings: 9, all root-fixed.
- Minor findings: 3, all fixed.
- Waivers: none.
