# M2.3 Review Round A — Open Issue Mining

## Scope

This review evaluated M2.3 Research Planning/Runtime without scores. It inspected the boundary between Research Results and Evidence, deterministic orientation/targeted planning, cycle identity, provider identity, Run persistence, immutable query cache, TTL and invalidation, failure checkpoint/resume, offline behavior, resource bounds, workspace validation, M2.2 compatibility and package audit coverage.

Production Web-search vendor adapters and Evidence adjudication were excluded because they are explicit M2.3 non-goals.

## Findings

### Critical

None.

### Major — raw research execution could have collapsed into Evidence truth

- Problem: the pre-M2.3 contract had `ResearchProvider` and semantic `research_cycles` but no runtime layer. A direct implementation could have written search results straight into Evidence and made “search completed” indistinguishable from “claim verified”.
- Root fix: ADR-0011 and the runtime contract explicitly separate `ResearchResult` from Source/Evidence. M2.3 never updates Source Ledger claims or marks semantic research cycles complete; M2.4 owns materialization, support/conflict/freshness/authority/use-policy decisions.
- Verification: Skill, architecture, artifact, degradation and compatibility docs repeat the same boundary; G2/G5A remain unchanged.

### Major — cache identity did not initially bind all cache-policy inputs

- Problem: the first cache key bound provider/query and content-size limits but omitted TTL. A stricter TTL plan could therefore reuse a snapshot created under a longer freshness window. Historical cache snapshots also did not carry enough result-limit data to recompute their own input key.
- Root fix: cache `result_limits` now persist max results/title/summary/metadata and TTL; input keys bind them; cache validation recomputes the key and verifies `expires_at == created_at + TTL`.
- Verification: provider-version and TTL-change tests force new cache identities; tampered cache lineage fails closed.

### Major — post-provider validation failures could leave a false `running` state

- Problem: provider exceptions were checkpointed, but unsafe URLs, result-limit failures, metadata validation or cache publication errors occurred after the provider call and could leave the task/Run recorded as `running`.
- Root fix: one `_checkpoint_failure` path now clears result/cache refs, persists failed/partial state and records the error for provider, cache and result-validation failures.
- Verification: unsafe URL, oversized metadata and overflow result-stream tests assert a persisted failed Run and no false cache publication.

### Major — provider results were not bounded before materialization

- Problem: converting an arbitrary provider iterable directly to a tuple could consume an unbounded response; provider metadata also had no byte limit and non-JSON values could escape the intended runtime error contract.
- Root fix: result iterables are consumed only through `islice(max_results_per_query + 1)`; `ResearchLimits` includes `max_metadata_bytes`; metadata must be JSON-serializable and within the byte budget.
- Verification: a 1,000-item generator with a limit of two is rejected after the overflow sentinel, and oversized/non-JSON metadata fail with checkpointed state.

### Major — research cycle IDs could be rebound to incompatible semantics

- Problem: an explicitly supplied cycle ID was only syntactically checked. A targeted plan could reuse the existing orientation `RSC-001`, or create arbitrary gaps unrelated to Evidence Ledger lineage.
- Root fix: requested IDs must match an existing cycle's kind/outline version, or equal the next available cycle ID when introducing a future semantic cycle. Default targeted lookup requires the exact current outline version.
- Verification: targeted reuse of orientation `RSC-001` and arbitrary `RSC-999` both fail deterministically.

### Major — workspace validation was not purely read-only

- Problem: global `validate_workspace()` initially called the same inspect path that reconciles invalidation markers. A validation command could therefore rewrite a Research Run.
- Root fix: workspace validation now uses a pure runtime/cache verification path. Explicit load/inspect/resume may reconcile recoverable marker/Run ordering; validation never does.
- Verification: an intentionally interrupted invalidation marker is accepted as recoverable by workspace validation without changing Run bytes, then explicit `load_run()` performs reconciliation.

### Major — M2.3 protocol work temporarily regressed the completed M2.2 contract

- Problem: a full rewrite of `protocols.py` preserved M2.1 fields but dropped the M2.2 `DetectedSourceFormat.detection_method` compatibility accessor. The full suite exposed 28 cascading source failures.
- Root fix: the complete M2.2 source DTO contract is preserved and `detection_method` is a stable alias of the snapshot-compatible `signature` field; M2.3 adds only research DTOs/provider identity.
- Verification: the complete multi-format/MVP/source suite returned green before review continued.

### Major — unresolved Brief placeholders could become external queries

- Problem: default values such as `待补充` are non-empty strings. A planner that only tests truthiness can send placeholder text to a ResearchProvider.
- Root fix: planning rejects known placeholder context and fails if no meaningful bounded query can be formed.
- Verification: an external-research-enabled but otherwise unresolved stage-0 Brief fails planning instead of generating a query.

### Major — invalidation recovery did not initially validate marker semantics strongly enough

- Problem: generation markers are the authority that makes old immutable cache snapshots ineligible. A malformed marker or interruption after marker publication must neither silently re-enable old cache nor corrupt a Run.
- Root fix: marker input key, positive generation, timestamp and reason are validated; load reconciles a higher generation into `invalidated/planned`; historical snapshots stay immutable.
- Verification: crash-order simulation, malformed-marker and generation-refresh tests pass.

### Minor — runtime schemas were outside the package schema audit

- Problem: the package audit validated only catalog artifact schemas, while Research Run and Cache Snapshot are intentionally non-catalog runtime schemas.
- Root fix: the existing `schemas` audit now validates every `*.schema.json` while reporting the subset registered as catalog artifacts; schema mirrors remain byte-identical.

### Minor — cache query schema did not independently enforce two-pass outline semantics

- Problem: a historical orphan cache could be schema-valid with `cycle_kind=targeted` and `outline_version=null` even though a referenced Run would reject it.
- Root fix: the cache query schema now carries the same orientation-null / targeted-positive-outline condition as the Run contract.

### Minor — operator inspection had no stable Research Runtime CLI surface

- Problem: planning and runtime facts would otherwise require direct Python calls to inspect or invalidate safely.
- Root fix: `slidethus research plan/list/show/invalidate` exposes deterministic planning and verified runtime inspection without adding a hard-coded online search vendor.

## Regression evidence after fixes

- M2.1/M2.2 source identity, immutable snapshots and failure recovery remain intact.
- Multi-format adapters and MVP1 continue using the completed SourceParser contract.
- Research unit tests cover planning, cache hit/stale/invalidation, provider drift, resource bounds, failure resume, offline behavior, tamper detection and validation purity.
- Complete Python 3.11 suite passes together with compileall, Ruff and `validate_all.py`.
- Isolated package audit passes 18/18 and validates all packaged runtime schemas.

## Result

- Critical findings: 0.
- Major findings: 9, all root-fixed.
- Minor findings: 3, all fixed.
- Waivers: none.

Round B may proceed only after the final full Python 3.11 verification and package audit are rerun against the completed documentation/ADR diff.
