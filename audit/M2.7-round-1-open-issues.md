# M2.7 Review Round A — Repository-wide Open Issue Mining

## Scope

This review evaluated M2.1–M2.6 as one Production Source/Research/Evidence boundary without scores. It intentionally ignored submodule PASS scores and inspected cross-module bypasses, direct CLI/service use, legacy runtime facts, current and historical lineage, provider/disclosure semantics, resource limits, workspace paths, Gate behavior, package verification and the handoff to M3.

New Source formats, a built-in search vendor, LLM claim extraction, M3 generation, rendering and visual review were excluded because they are outside the M2 Exit Gate.

## Findings

### Critical

None.

### Major — passing submodules did not constitute a repeatable M2 Exit Gate

- Problem: M2.1–M2.6 had individual Build/Review evidence, but no single deterministic command proved that the repository-wide contracts and completion evidence remained present and aligned.
- Root fix: `scripts/validate_m2_exit.py` now checks required plans/audits/ADRs/services/tests, runtime schemas/mirrors, completion state, provider neutrality, cross-module safety markers, example workspace M2 Gate and persistent verification wiring.
- Verification: `tests/test_m2_exit.py` contains one positive repository check plus missing-evidence, stale-task and bundled-network negative controls.

### Major — completion state was inconsistent across authoritative surfaces

- Problem: `TASKS.md`, roadmap, master M2 plan, README, Skill and Codex kickoff described different maturity states. A new agent could restart M2 or infer that M2 completion implied the whole PPT product was Production-ready.
- Root fix: current status sources now agree on `M2 Exit Gate: PASS`, explicitly freeze M2, point Codex to M3 and retain M3–M5/product non-goals.
- Verification: the Exit validator parses TASKS, roadmap, master plan, README, Skill and kickoff markers.

### Major — Package Audit and standard verification did not persist the complete M2 Gate

- Problem: Package Audit required evidence only through earlier M2 modules, and `make verify` did not execute a repository-level M2 check.
- Root fix: Package Audit now requires M2.1–M2.7 plans/audits/ADRs/schemas/services/tests and invokes the M2 Exit validator as a dedicated check. `Makefile` adds `m2-exit` to `verify`.
- Verification: Package Audit fails when final M2 evidence is absent; Exit validation checks its own Makefile/package wiring.

### Major — final M2 audit/build evidence and negative controls were absent

- Problem: without M2.7 Round A/Round B, a final Build Report and validator tests, “M2 PASS” would be a prose assertion rather than an inspectable decision.
- Root fix: dedicated M2.7 review files, `audit/M2-BUILD_REPORT.md` and `tests/test_m2_exit.py` are mandatory package evidence.
- Verification: both Exit and Package validators require these files.

### Major — high-risk Source protection existed only in the application orchestrator

- Problem: `M2ApplicationService` excluded high-risk Sources, but direct `EvidenceEngine.adjudicate`, `slidethus evidence source` or Research materialization could still promote the same Source without an explicit override.
- Root fix: the policy moved to the Evidence Engine boundary. Direct Source and Research paths require `allow_high_risk_source_evidence`; CLI exposes the explicit flag rather than silently bypassing it.
- Verification: direct Engine and CLI tests fail without the override and succeed only through the explicit path.

### Major — Research provider summaries bypassed Source-risk detection

- Problem: Research summaries became partial Web Source Chunks with `risks=()`, so instruction-like or active-content wording from a provider was not represented in Source lineage.
- Root fix: Research Result materialization uses the same deterministic `build_source_risks` scan as local ingestion and increments Source Snapshot/Ledger risk facts. The materializer version was advanced so old snapshots cannot masquerade as the new policy.
- Verification: a malicious provider summary remains inventoried as a partial Web Source but Evidence adjudication blocks until the explicit override.

### Major — an old high-risk override could become a permanent default permission

- Problem: after one explicit override created usable Evidence, a later default M2 application run could reuse that claim even though the high-risk Source should again be excluded.
- Root fix: application-level safe-claim selection ignores Evidence whose current support is exclusively from excluded high-risk Sources. Existing page bindings backed only by excluded Sources block planning acceptance unless the current run explicitly authorizes the override.
- Verification: a second default run after an override is blocked and records the excluded Source.

### Major — high-risk Evidence policy was not independently validated

- Problem: a rehashed or legacy Production claim backed by a high-risk Source could claim `verified` support or omit the high-risk qualification reason.
- Root fix: workspace validation derives high-risk Source IDs from immutable snapshots and rejects verified or incompletely adjudicated high-risk Evidence. The Engine always records `high_risk_source_requires_qualification` and keeps support provisional or stricter.
- Verification: Artifact Runtime rejects a candidate Ledger that attempts to upgrade high-risk support to verified/citation-only semantics.

### Major — stale or legacy Evidence could block application repair before G0

- Problem: application startup evaluated Gates before it had a public way to reconcile stale Production candidate bindings. A legacy invalid claim could make the workspace fail validation before the integrated repair path ran.
- Root fix: `EvidenceEngine.reconcile_current_evidence` re-adjudicates current persisted bindings without adding Candidates. M2 application startup invokes it before Gate progression; CLI exposes `evidence reconcile`.
- Verification: Source changes are repaired into unsupported historical Evidence plus a new current claim, and G2 can be re-established without deleting stable IDs.

### Major — mutable provider identity could split one Research Run from its cache lineage

- Problem: Research Runtime repeatedly read `provider.name/version`. A provider object that mutated during `search()` could produce a Run with one identity and cache snapshots with another.
- Root fix: Research Runtime captures a normalized immutable provider identity at construction and uses it for Run IDs, input keys, Run facts, cache publication and list filtering. M2 application separately detects provider-object identity mutation and blocks report acceptance.
- Verification: dedicated Research Runtime and M2 application tests mutate provider version during execution; Run/cache remain internally consistent and the application records a blocker.

### Major — M2 Application Reports referenced live mutable Research Run files

- Problem: a report stored only `research_run_ids`. Later invalidation legitimately rewrites the live Run, so a historical ready report no longer had the exact Run fact it evaluated.
- Root fix: every referenced Run is copied once into `.slidethus/m2/research-runs/<content-hash>.json`. Report refs bind snapshot hash/status/cycle, and archived Run tasks bind immutable Research Cache paths/hashes.
- Verification: live invalidation changes the operational Run while the historical M2 report continues to verify against the immutable archived snapshot.

### Major — Application Report facts were not independently recomputable

- Problem: a validly rehashed report could alter config/security decisions, omit Source/Evidence IDs or claim budgets that did not match the final Ledger/Run facts.
- Root fix: reports now persist the complete typed application config plus hash. Validation recomputes provider/disclosure/high-risk decisions, requested/current/final Source budgets, Source/Evidence ID sets, Research query/result/title/summary/metadata limits and required artifact refs.
- Verification: forged config, output-ID and budget reports fail even after recomputing report ID and filename.

### Major — runtime output paths could escape the workspace

- Problem: forged Gap, Research Run snapshot or Research Cache paths could use absolute paths or `..` traversal and cause validation to read outside the workspace.
- Root fix: all report/runtime path validation uses `ensure_within` and exact admitted roots for `.slidethus/evidence/gaps`, `.slidethus/m2/research-runs` and `.slidethus/cache/research`.
- Verification: validly rehashed Gap and Research snapshot traversal attempts fail workspace validation.

### Major — application reports could omit side effects from failed Research integration

- Problem: a Research Run could complete and materialize a Web Source before Evidence adjudication failed; the final report might omit the Run or Source because the helper raised before returning them.
- Root fix: the application records observed Run IDs immediately after execution and refreshes final Source/Evidence/Run inventory from current semantic lineage before report publication.
- Verification: malicious Research summary tests show the blocked report still contains the Run and inventoried Web Source.

### Major — application concurrency did not protect Brief/provider policy identity

- Problem: Brief or provider identity could change during a long Research call, while the application still reported a decision based on the initial policy.
- Root fix: the final Project Brief artifact ref must equal the initial ref, and provider name/version must equal the captured config identity. Any drift records an explicit D5 blocker.
- Verification: providers that mutate the Brief or their own version during search cannot produce an accepted report.

### Major — final inventory could exceed application limits after Research materialization

- Problem: preflight/current checks occurred before external Research added Web Sources. Final Source count/bytes or archived Run query/result limits could exceed the application policy after side effects.
- Root fix: the final Source Ledger and every archived Research Run are rechecked before status selection and report publication.
- Verification: a small final Source budget blocks after Web materialization while retaining the complete auditable side effects.

### Major — repository maturity and deck workflow Gates could be conflated

- Problem: introducing an ad hoc `G-M2` into deck state would mix repository maturity with one project’s G0–G9 phase.
- Root fix: M2 Exit remains a repository validator/audit decision. Individual workspaces continue to use G1/G2 and current G5A.
- Verification: plan/ADR/validator wording and example workspace checks preserve the separation.

### Major — M2 completion wording could overclaim Narrative/Rendering/Product maturity

- Problem: marking M2 complete without retaining MVP and M3–M5 limitations could imply Production narrative, rendering or visual repair.
- Root fix: README, Skill, roadmap, kickoff and final Build Report state that M2 Source/Research/Evidence is complete while M3–M5 ProductionImpl, provider adapters and the full product remain incomplete.
- Verification: Exit validation requires both M2 PASS and explicit non-product-completion wording.

### Minor — duplicate and reordered requested paths produced unstable application identity

- Problem: repeated or differently ordered `--source` values could consume count budget and allocate Source IDs in caller order.
- Root fix: requested paths are canonicalized, deduplicated and sorted before preflight/ingestion.

### Minor — the first Exit validator assumed the wrong roadmap heading

- Problem: it searched for a nonexistent `## M2` heading while the roadmap records M2 under `## v0.5 Planning Pipeline`.
- Root fix: the validator parses the actual authoritative section.

### Minor — the initial Exit contract referenced a wrong ADR filename

- Problem: the draft required `ADR-0012-deterministic-evidence-materialization.md`; the accepted file is `ADR-0012-deterministic-evidence-adjudication.md`.
- Root fix: required paths use the actual accepted ADR.

### Minor — two M2.7 planning drafts used different script names

- Problem: one draft named `audit_m2_exit.py`, while the implemented persistent Gate is `validate_m2_exit.py`.
- Root fix: `plans/M2.7-m2-exit-gate.md` is canonical; the other file is retained only as an explicit superseded audit trail.

### Minor — repository host Python is below the admitted baseline

- Problem: the OCI host Python 3.10 cannot serve as the formal Python 3.11+ release baseline.
- Root fix: all formal M2.7 verification runs in isolated Python 3.11 and 3.12 containers; reports do not treat host results as release evidence.

### Minor — final package manifest was stale during M2.7 edits

- Problem: new scripts/tests/audits/schemas/docs changed the file set after the M2.6 manifest.
- Root fix: Package Audit regenerates automated reports and `manifest.sha256` only after the final M2.7 state is frozen.

## Cross-module invariants retained

- Recognized format is separate from admitted parser capability.
- `partial` never means OCR, vision, formula evaluation or fetched Web body.
- Research Result remains separate from Source body and Evidence.
- Provider capability remains separate from disclosure approval.
- Source updates invalidate Evidence lineage and G2 until reconciliation.
- High-risk Source instructions are never executed; explicit use remains qualified.
- Required block Evidence, qualification and current targeted-cycle checks remain G5A prerequisites.
- P2 rework remains an Artifact Runtime transition with Decision Log lineage.
- No unit test performs a network call.
- M2 does not generate or silently edit M3 artifacts.
- Source-preserved material remains unchanged.

## Result

- Critical findings: 0.
- Major findings: 17, all root-fixed.
- Minor findings: 6, all fixed or explicitly treated as historical/environmental facts.
- Waivers: none.

Round B may proceed only after final status synchronization, positive/negative Exit validator controls, complete Python 3.11/3.12 suites, workspace validation, Package Audit and diff review pass.
