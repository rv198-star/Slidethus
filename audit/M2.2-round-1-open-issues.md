# M2.2 Review Round A — Open Issue Mining

## Scope

Review M2.2 Multi-format Source Adapters without scores. The review inspected format admission, optional dependencies, native locators, source identity, source mutation, parser resource budgets, OOXML container safety, formula/link isolation, content-coverage claims, `parsed/partial` persistence, CLI/MVP integration, Schema compatibility and third-party notices.

The review did not evaluate OCR, image understanding, audio/video interpretation, formula calculation, Web research or the Evidence Engine because those capabilities are explicit non-goals of M2.2.

## Findings

### Major — format recognition and parsing capability were previously conflated

- Problem: M2.1 could identify PDF, OOXML, HTML, CSV and images but only admitted Markdown/TXT. A generic fallback would have lost native locators and container risks; leaving every format unsupported blocked the planned Production path.
- Root fix: independent HTML, CSV/TSV, PDF, DOCX, PPTX, XLSX and raster-image metadata adapters now implement the existing `SourceParser` protocol and enter one deterministic Parser Registry. SVG, legacy OLE, macro-enabled OOXML, encrypted PDF and unknown families still fail closed.
- Verification: real programmatically generated fixtures and explicit unsupported-format tests cover every admitted family.

### Major — the complete MVP used a narrower registry than `source ingest`

- Problem: the standalone source CLI used the full registry, but `build_minimal_mvp` constructed `ParserRegistry([TextSourceParser])` by default. Multi-format ingestion therefore worked in isolation but failed at the actual application entry point.
- Root fix: the MVP now uses `default_parser_registry()` unless a caller explicitly injects one parser for a bounded test or custom path.
- Verification: a CSV source reaches the complete G0–G9 MVP with independent preview fixtures and keeps all evidence references bound to `SRC-001`.

### Major — resource budgets did not cover format-native expansion

- Problem: bytes/Chunks/characters alone did not bound pages, slides, sheets, rows, cells, risks, ZIP entries, one expanded ZIP member, total expanded bytes or image pixels. Several adapters also accumulated blocks or metadata before discovering `max_chunks`/`max_risks` overflow.
- Root fix: `SourceParseLimits` now covers all format-native dimensions; adapters check rows/cells/pages/slides/sheets and append blocks/risks through bounded helpers. PDF extracted text is bounded by the decoded-content budget and estimated Chunk count. Image pixel/frame limits are checked before verification/decompression work continues.
- Verification: max block, risk, archive entry/member/total expansion, PDF extracted bytes, page/sheet/row/cell and image-pixel tests fail deterministically.

### Major — OOXML preflight admitted ambiguous or dangerous packages

- Problem: initial preflight did not reject duplicate/case-colliding members, symlinks, drive-qualified paths, oversized individual members or macro-enabled content types. Relationship XML inspection was too narrow, and external targets were counted but not preserved for audit.
- Root fix: preflight now rejects duplicate names, absolute/traversing/drive-qualified paths, symlinks, encryption, VBA parts, macro content types, excessive entries/member/total expansion and DTD/entity declarations. External targets are recorded verbatim within a bounded risk message and never opened.
- Verification: traversal, corrupt ZIP, duplicate member, macro content type, archive limits and external relationship fixtures are covered.

### Major — format selection and source bytes could diverge during parsing

- Problem: Registry selection initially read the file header, while the chosen adapter later captured the full payload. The file could change family between those operations, or change again before snapshot publication, allowing an old parser contract or stale path to accompany new bytes.
- Root fix: every adapter revalidates the detected-format contract against the same captured payload it parses. `SourceIngestionService` then fingerprints the path after parsing and rejects a changed hash/size before any snapshot or Ledger version is published.
- Verification: one fault-injection parser changes TXT into PDF after Registry selection, and another changes content after parsing; both leave Source Ledger and ingestion cache unchanged.

### Major — successful parsing did not distinguish complete from partial coverage

- Problem: metadata-only images, PDF pages without text, Office images/comments/endnotes/equations/SmartArt/media and cached chart data could be useful while still omitting material content. Marking all of them `parsed` would falsely imply OCR, visual understanding or full document interpretation.
- Root fix: `SourceParseResult`, Source Snapshot and Source Ledger now carry `parsed` or `partial`. Partial status is used whenever admitted facts exist but recorded content classes remain uninterpreted. Files with no usable admitted facts fail instead of producing an empty snapshot.
- Verification: image, DOCX, PPTX, XLSX and incomplete PDF paths assert partial/failure semantics; workspace validation requires snapshots for both production `parsed` and `partial` sources.

### Major — native locator and value semantics were insufficient for evidence use

- Problem: CSV multiline records could not be traced to physical lines; XLSX raw numerics omitted number formats and could turn `0.15`/`0%` into an ambiguous fact; PPTX chart extraction omitted categories; long format-native blocks could exceed later Chunk capacity.
- Root fix: CSV locators include logical rows and physical line ranges; XLSX cells preserve raw value plus non-General `number_format`; PPTX chart blocks include categories and series values; shared Chunk construction adds character ranges for split blocks.
- Verification: multiline CSV, signed numeric non-formulas, percentage formatting and chart-category tests pass.

### Major — formulas, links and embedded Office data had inconsistent risk semantics

- Problem: a simple prefix rule treated negative numbers as formula injection; external targets were recorded without their destination; normal PPT chart workbooks were initially indistinguishable from high-risk ActiveX/unknown binaries.
- Root fix: formula-like detection distinguishes signed numerics from executable spreadsheet prefixes; HTML and OOXML preserve link targets without opening them; standard embedded Office data used by charts is a warning while ActiveX/unknown binary embeddings remain high severity. Formulas are always preserved verbatim and never evaluated.
- Verification: negative/positive numeric CSV values, formula cells, external targets and normal chart-workbook severity are covered.

### Major — omitted Office/PDF content classes were not consistently surfaced

- Problem: comments, footnotes/endnotes, equations, charts/SmartArt, media, PDF annotations/forms/rich media and image-only pages could be silently absent from extracted text.
- Root fix: adapters inspect package parts or PDF markers, emit bounded warnings and set `partial`. DOCX covers paragraphs, tables, headers/footers, header/footer tables, textboxes and image alt text; PPTX covers shapes, grouped shapes, tables, chart cache data, notes and image metadata; XLSX covers visible/hidden worksheets, cells, formulas and number formats.
- Verification: fixtures containing images, comments, charts, hidden sheets, notes and blank PDF pages assert the expected coverage boundary.

### Minor — optional dependency absence lacked an operator-facing capability inventory

- Problem: adapters raised an actionable error, but `slidethus doctor` did not tell operators which multi-format capabilities were available before a run.
- Root fix: `doctor` reports PDF, DOCX, XLSX and image dependency availability as optional capability checks without making them requirements for the base deterministic install. HTML/CSV/PPTX base capability is reported separately.
- Verification: CLI tests assert the capability inventory and preserve a successful base doctor result.

### Minor — dependency and capability documentation was stale

- Problem: README, Skill guidance, capability/degradation docs and notices still described multi-format sources as unsupported and did not enumerate new direct optional dependencies or `partial` semantics.
- Root fix: architecture, artifact, quality, security, degradation, roadmap, compatibility, risk register, Skill reference, README and third-party notices now share the same admitted-format and non-goal boundaries. ADR-0010 records the decision.
- Verification: package audit, relative-link checks, Skill layout checks and Schema mirror checks pass.

### Minor — snapshot integrity originally covered only complete parses

- Problem: workspace validation required an immutable snapshot for production `parsed` records but could allow a `partial` record with a `sha256:` lineage and no snapshot.
- Root fix: both production `parsed` and `partial` records require a valid source snapshot, and snapshot/ledger parse status must agree.
- Verification: a synthetic partial record without a snapshot is rejected.

## Regression checks

- M1 Artifact Runtime remains the only writer of Source Ledger facts.
- M2.1 Markdown/TXT identity, immutable cache, policy update and crash-recovery behavior remain intact.
- No adapter performs network access, macro/script/formula execution, embedded-object execution, OCR or image/media understanding.
- Existing M0/MVP snapshots remain Schema-compatible; expanded default limits cause safe reparsing instead of incorrect cache reuse.
- MVP1 still fails G8/G9 honestly when independent previews are unavailable.
- No source-preserved third-party material was modified.

## Result

Critical findings: 0. Major findings: 9, all fixed. Minor findings: 3, all fixed. No waiver was used. Round B may proceed after the final Python 3.11 suite, package audit and diff review pass.
