## 1. 总结论

**Gate：FAIL — REVISE BEFORE ADR / IMPLEMENTATION。**

1. scoped Calibration Attempt、审批事实、full-deck Attempt 与项目级 G7–G9 尚未形成单向、隔离的状态图；

## 2. Critical findings

### C-01｜Calibration Run 与审批事实存在引用环和重复权威

**位置**：计划 230–244、248–253、278–281 行。
**最早责任层**：Artifact graph / Calibration contract。

当前 `CalibrationRun` 保存 `decision_log_ref`，而 Decision Log 又被要求引用当前 Calibration Run。若两者不可变并进入 hash lineage，则无法按单向顺序发布；若 Run 后写更新，则 `status`、批准结果和当前性又会在 Run 与 Decision Log 之间重复。

失败反例：

1. Run 先结束，但尚无 Decision；
2. Decision 随后引用 Run；
3. 为了让 Run 再引用 Decision，必须改写已终止 Run 或产生第二个 Run；
4. G9 此时无法确定哪个对象是审批的唯一事实源。

**最小修订**：

- `CalibrationRun` 只记录 scope、selector proof、终止 Attempt、Render、Office 与 Review refs；
- 新增单向、不可变的 `CalibrationDecision`，引用已终止 Run 与批准时的完整 artifact-set hash；
- G9 只消费 `CalibrationDecision`；
- Decision Log 仅记录 Decision ID/摘要，不允许 Run 反向引用 Decision Log。

### C-02｜scoped Calibration Attempt 会污染项目级 current artifacts 与 G7–G9

**位置**：计划 246–253、270–291、334–347 行。
**最早责任层**：State machine / Gate architecture。

当前 catalog `Render Manifest`、`Quality Report`、Project State 与 Gate results 都是项目级 current 语义，没有 attempt kind、slide scope 或 attempt ref。选中 1..N 页的 calibration 若复用现有 Production Attempt 路径，可能把局部渲染写成项目当前 G7/G8；若不复用，又没有合法的 scoped render truth。full-deck Attempt 随后会覆盖同一事实源。

失败反例：

- 只渲染 4 页的 Calibration Attempt 写出 catalog Render Manifest，项目被误判为已完成 G7；
- calibration review 等待批准时，现有 Create runtime 没有独立的 resume contract；
- full-deck Attempt 重跑后，无法证明 G9 审批对应的到底是 scoped 结果还是 current full result。

**最小修订**：

- 定义不可变 `ProductionAttemptSnapshot` 或等价事实：`attempt_kind=calibration|full`、slide scope、完整上游 refs、execution signature、terminal state；
- calibration 输出留在 attempt-scoped、non-catalog 路径，不更新 Project State，也不发布项目级 Render/Quality/Delivery；
- Review evidence 必须携带 attempt ref；
- 只有覆盖全部 active slides 的 `full` Attempt 可发布 catalog artifacts 并推进项目 G7–G9；
- full run 通过显式 `resume_calibration_run_id`/decision ref 启动；selector 若覆盖全 deck，应直接提升为 full Attempt。

### C-03｜hard Policy 仍是自由文本，G5A/G6/G7 无法独立判定

**位置**：计划 105–132、145–158、191–228、270–280 行。
**最早责任层**：DesignPlanningPolicy Schema / deterministic resolver。

`required/forbidden` 当前只有自由文本 `statement`，但 deterministic core 被限制为 admission、lineage、限额和冻结。于是“Packet 是否反转 hard policy”“rule 是否真正执行”无法由 Gate 重算，只能相信 `resolved_policy_items`、trace IDs 或 Reviewer 的语义自报。

失败反例：Policy 写“required：保持高雅编辑节奏”，Packet 声称 resolved，Renderer 仍输出统一卡片；由于没有 target/operator/value 与具体 scope，G6/G7 仍可能通过。

**最小修订**：

- `scope` 改为有目标的结构：`kind + slide_ids/slide_types/...`；
- 只有含机器可解释 `target/operator/value/scope` 的 constraint 才能成为 `required/forbidden`；
- 纯文本判断只能是 `preferred/avoid`；
- `resolved_policy_items` 记录 `implemented|deviated|not_applicable`、decision/rule refs 与适用性；
- 建立纯函数 resolver，G5A/G6/G7 从 current artifacts 重算适用约束、预期效果与偏差，不读取自报 PASS。

## 3. Major findings

### M-01｜Planning Policy 缺少唯一 current 选择、稳定输入快照和失效矩阵

**位置**：计划 99–110、125–132、274–275、335–348 行。
**最早责任层**：Artifact runtime / dependency graph。

Policy 可有多个 content-addressed 版本，但 P5A 仅引用泛称 current Policy，没有唯一 selection fact。`available Asset Manifest` 也可能在 representation 决策后变化，形成上游 Policy 被下游资产变化反向失效的隐性反馈边。

**最小修订**：

- 建立唯一 `planning_policy_ref` 选择事实，绑定 version/hash/input signature；
- Policy 只读取 G4 冻结的 asset inventory snapshot，或移除该输入；
- 列出 Brief/Narrative/Outline/asset snapshot/Policy 变化对 G5A–G9 的撤销矩阵。

### M-02｜同一 ArtDirectionProvider 的两阶段 operation 与复现语义未定义

**位置**：计划 51、54–55、97–134、189–205、336 行。
**最早责任层**：Provider protocol。

现有 provider 语义偏向 P6 full-context proposal；新方案又在 G4 后要求 Planning Policy。若不拆 typed operations，provider 的输入权限、输出能力和 resource/model identity 都不清楚。对非确定 provider 直接要求 same-input idempotence 也不成立。

**最小修订**：

- 在同一 provider-neutral 协议内定义 `planning_policy` 与 `final_direction` 两种 request/response DTO；
- 限制每种 operation 可读输入；
- 记录完整 execution identity；
- deterministic service 按 input signature 复用已冻结结果，不假设 provider 自身确定。

### M-03｜Packet 与 Visual System 同时拥有 executable grammar

**位置**：计划 189–205、220–228 行。
**最早责任层**：P6 contract。

Packet 的 treatments/variants/rhythm 被描述为 Renderer 可执行结构，而 Visual System 又被定义为其确定性编译结果；Reviewer 还从 Packet 读取 rule IDs。规则定义、rule ID 与 effect 参数因此没有唯一事实源。

**最小修订**：

- Packet 只拥有 admitted direction、Policy resolution 与 deviation rationale；
- Visual System 独占 executable grammar、selector、declaration、rule ID 与 effect；
- Renderer 只读 Visual System；Review 通过 lineage 连接 Packet，不复制规则定义；
- P6 的 `approval_ref` 只能引用 G6 前已存在的授权事实，不得引用未来 CalibrationDecision。

### M-04｜Representation 适用域、fallback 与实际载体事实可能分叉

**位置**：计划 136–187、285–292 行。
**最早责任层**：P5A/P5B representation contract。

“每个需要规划判断的 Block”不可机械确定；P5A 的 `content_type` 被定义为实际载体，但 fallback 又可声明另一个 `content_type`，P5B 再自报 `fallback_status`。Renderer 若临时 substitute/omit，Specs 仍说 chart/image，实际输出却成为 text 或空缺。

**最小修订**：

- 新 Create 路径要求所有 active、非 spacer/纯装饰 Block 拥有 `representation.planning_status`；
- legacy 只能是 `unplanned`，G5A 必须阻断；
- fallback 只保存控制动作，不成为第二个实际载体；substitute/omit/replan 必须产生新 Slide Specs/Layout 版本；
- 删除 P5B 自报的 authoritative fallback status，Gate 从 Asset Manifest、Evidence 和 fallback rule 重算；
- 区分 asset default fit 与 placement fit，并把 focal/crop 绑定具体 asset ref/hash。

### M-05｜IR trace 未覆盖装饰对象、一对多编译和可执行效果重算

**位置**：计划 207–228、279、325 行。
**最早责任层**：Renderer IR Schema / trace verifier。

不是每个 IR 对象都有 Block/Region：背景、关系标记和节奏装饰可以由 Visual System 产生；一个 list/chart Block 也可能编译成多个对象。当前“每个实际对象记录全部 refs”会迫使伪造 Block refs，或漏验部分对象。

**最小修订**：

- 至少定义 `semantic object` 与 `visual-system object` 两类 trace origin；
- 允许 Block/Region → 多个稳定 `object_id/object_kind`；
- 将 rule 分为 object、geometry、deck constraint，使用受限 selector/declaration；
- Reviewer 重跑 resolver 并比较预期属性/effect fingerprint，而不是只检查 rule ID；
- 不适用或语义等价 rule 变化不得被错误要求改变 IR。

### M-06｜Office-first 缺少 current PPTX 的强 provenance

**位置**：计划 239–253、278–280 行。
**最早责任层**：Render Manifest / Visual Review contract。

仅有 preview path/hash、slide IDs 和 `office_preview available/pass`，仍可提交旧 Render 的 Office 页面。Office 是主事实源并不等于它自动属于 current Attempt。

**最小修订**：

- Office pages 绑定 attempt ref、current Render ID、目标 PPTX path/hash、renderer identity、页序与 slide ID；
- Reviewer 从 Manifest 自行发现并校验覆盖，不接受调用方自由拼 refs；
- provider 输入明确区分 `primary_office_images` 与 `comparison_svg_images`。

### M-07｜Selector 的“最小集合”缺少可复现算法和 coverage proof

**位置**：计划 235–237、248–268 行。
**最早责任层**：Calibration selector contract。

当前只列举特征，没有有限特征字典、分桶、稳定 tie-break、uncovered feature 行为和 selector identity。不同遍历顺序可能产生不同集合，长文本等连续值还可能导致每页都被当作独立特征。

**最小修订**：

- 冻结版本化、有限、分桶的 feature dictionary；
- 使用确定性 greedy cover 与 stable slide-ID tie-break；
- 输出 candidate feature hash、coverage targets、selected/unselected rationale 与 uncovered features；
- required feature 无候选时 blocked；选中全 deck 时提升为 full Attempt。

### M-08｜审批权限、通过条件和失效规则没有单一持久事实

**位置**：计划 248–253、278、281、291 行。
**最早责任层**：Workflow request / authorization contract。

`calibration_policy` 来自泛称 Workflow Request，但没有 Schema/hash，也没有与 Project Brief `approval_mode` 的优先级。计划把“Review 完成”写成可进入下一步，却未明确 Critical/Major=0；批准后若 Layout、Visual System、backend 或字体变化，旧 approval 仍可能被 G9 接受。

**最小修订**：

- calibration policy 持久化进 application request/config 和 attempt signature；
- 明确它与 `auto|checkpoint|strict` 的组合与权限规则；
- full run 的前置条件为 current Review `Critical=0 && Major=0` 加显式 approval；
- approval 绑定 Specs/Layout/Policy/Packet/Visual System hashes、backend 与 execution signature；任一漂移自动 supersede；
- checkpoint 未批准时唯一结果为 blocked，不允许含糊的“不启动或保持 draft”。

### M-09｜Schema migration 与 Gate 撤销没有实际承载机制

**位置**：计划 287–292、335、345–348 行。
**最早责任层**：Schema evolution / migration registry / stop policy。

当前只规定旧 Block 迁移为 `unplanned`，但没有说明旧 Layout、Packet、Visual System、IR、Render、Review、Delivery 与 G5A–G9 如何失效；项目现有 migration 机制也不能自动重写所有 artifact body。

**最小修订**：

二选一写入 ADR：

1. Schema 字段保持 optional，但新 Create capability gate 要求 P5A/P5B 重跑；或
2. 实现真正的 per-artifact migration，发布新版本并保留旧历史。

两种路径都必须规定：旧项目停在 G4，Specs 及下游 supersede，撤销 G5A–G9；不得自动补造 rationale；generic legacy draft 不得声称通过本轮新 visual-intelligence path。

## 4. Minor findings

### m-01｜content addressing 与 `generated_at`/幂等语义冲突

Policy 同时被定义为 content-addressed、包含实时 `generated_at`，又要求 same-input idempotence。Identity hash 应只取 canonical semantic payload/input signature；运行时间作为非 identity metadata，或从稳定上游事实确定性派生。

### m-02｜same-case package audit 需要避免误报与隐性特判

计划正确禁止 production 出现案例主题词，但单纯关键词扫描无法发现 hash、标题模式或 fixture-derived 常量，也可能误伤测试和文档。应明确：

- CI invariant tests 使用 opaque case IDs 与冻结 provider proposals；
- 三个真实案例只做端到端 Office 评估和用户验收，不把具体颜色、像素、组件名写入核心断言；
- 加入主题文本替换、stable ID 重映射等 metamorphic tests；
- 案例词扫描只作用于 production logic/schema conditions，并对文档、audit、fixture 有明确 allowlist。

## 5. 两轮共同确认的通过项

以下内容不需要因本次审计推翻：

1. Create-only 与三案范围披露清楚，没有冒充全 workflow 或全行业验证；
2. `Policy → Block decision → Region binding → P6 → IR` 的主生产链方向正确；
3. P5B 明确禁止引用 P6 component、Calibration 和 Office 未来事实，关闭了原方案的主链时序环；
4. Block 级 representation 复用既有 content types，没有新增图片/图表配额或行业载体枚举；
5. `function` 不允许作为模板 lookup key；
6. Taste 保持在可替换 ArtDirectionProvider 内，Renderer 不依赖 Taste；
7. Calibration 由 request 显式开启，不按行业或“外部/内部”自动触发；
8. selector 以 1..N 集合覆盖为方向，不固定四页和固定页面角色；
9. Office 页面为主评审输入、SVG 为对照，方向符合 ADR-0027；
10. 假 trace、未来引用、rule no-op、Office/SVG 不一致和 production 案例分支等结构性负例有效；
11. component coverage、diversity、negative space 等只做诊断，不单独形成美学 PASS。

## 6. 进入 ADR 前的最小修订顺序

### A. 先关闭状态图

1. 定义 application request 中 calibration policy 与 approval authority；
2. 定义 attempt kind/scope/signature/terminal state；
3. 定义 non-catalog scoped outputs；
4. 改为 `CalibrationRun → CalibrationDecision → G9` 单向链；
5. 规定只有 full Attempt 能更新 catalog artifacts 和项目 Gate。

### B. 再收紧唯一事实源

6. 定义唯一 Policy current ref、G4 asset snapshot 与失效矩阵；
7. 将 hard Policy 改为机器约束并建立纯函数 resolver；
8. Packet 只表达方向/解析/偏差，Visual System 独占 executable grammar；
9. fallback 改为 replan 控制，不允许 Renderer 临时改变实际载体；
10. 定义 IR trace origin、一对多对象和 effect 重算。

### C. 最后补复现与演进合同

11. 定义 typed provider operations 与 input-signature cache；
12. 定义 deterministic selector 与 coverage proof；
13. 将 Office preview、Review 和 approval 绑定 current attempt/PPTX/artifact hashes；
14. 选择并实现一种 artifact migration 路径；
15. 冻结 focused acceptance matrix 后再进入 Schema/实现。

## 8. 当前轮决定

1. 不修改已冻结方案，不在审计过程中静默修复；
2. 不把行业/场景数量少升级为问题；
3. 当前方案保留为有价值但尚未通过 Gate 的执行草案；
4. 下一动作应是先按第 6 节修订方案，再重新做一次窄化 Gate review；
5. 只有 Critical=0、Major=0 后才进入 Step 2 ADR；
6. 本轮审计不改变 M6.6 release 状态，也不代表已完成实现或 Office release。
