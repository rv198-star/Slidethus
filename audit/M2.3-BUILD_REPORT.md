# M2.3 Build Report — Research Planning and Runtime

## Objective

Implement a real two-pass research execution layer that can plan, execute, cache, invalidate and resume provider-neutral research without confusing raw search output with verified Evidence.

## Delivered capabilities

### Deterministic research planning

- `plan_orientation_research()` derives bounded queries from the current Project Brief.
- `plan_targeted_research()` binds queries to the current registered Outline version and factual slide IDs.
- Stable `RPL-*`, `RQ-*`, `RT-*` and `RRN-*` identities support reproducible planning and recovery.
- Existing research-cycle IDs cannot be rebound to another kind or outline version; new IDs must use the next available sequence.
- Unresolved placeholders are not emitted as external queries.

### Provider-neutral runtime

`ResearchProvider` now declares `name` and `version`. The runtime executes one bounded query task at a time and checkpoints Run state before/after external provider work.

A provider failure, invalid result, corrupt cache or resource violation leaves inspectable `failed`/`partial` state rather than a false `running` status. Re-execution skips completed tasks and resumes the remaining work.

`OfflineResearchProvider` represents a host with no external research capability and returns no fabricated result.

### Immutable query cache

Research cache snapshots are stored as immutable content-addressed JSON under:

```text
.slidethus/cache/research/<input-key>/<content-hash>.json
```

Cache identity binds:

- query/cycle/outline/slide context;
- freshness requirement and preferred source tiers;
- provider name/version;
- per-query result, title, summary and metadata limits;
- cache TTL.

Each snapshot validates its own input key, expiry, result IDs and content-addressed filename. Explicit invalidation increments a generation marker while preserving old snapshots for audit.

### Resumable Research Runs

Runs are stored under:

```text
.slidethus/research/runs/RRN-*.json
```

They persist provider identity, plan hash, task states, attempts, cache references, result IDs and errors. A marker-published/run-not-updated interruption is reconciled on explicit load/resume.

Workspace validation checks Research Run and all cache history without mutating runtime state.

### Result/Evidence separation

M2.3 deliberately does not write Research Results into Source Ledger or Evidence claims. A Research Run `complete` proves execution completeness only.

M2.4 owns:

```text
Research Result
→ source materialization
→ Evidence normalization
→ dedupe/conflict/freshness/authority/use-policy
→ Evidence Ledger
```

Therefore M2.3 never auto-passes G2/G5A.

### Operator surface

```text
slidethus research plan <workspace> orientation|targeted
slidethus research list <workspace>
slidethus research show <workspace> <run-id>
slidethus research invalidate <workspace> <run-id> --reason ...
```

No production Web-search vendor is hard-coded into the CLI.

## Runtime schemas

- `schemas/research_run.schema.json`
- `schemas/research_cache_snapshot.schema.json`
- packaged byte-identical mirrors under `src/slidethus/_schemas/`

They are runtime schemas rather than semantic catalog artifacts. The package audit validates all repository schemas, so non-catalog does not mean unaudited.

## Safety and resource controls

- no network in unit tests;
- runtime itself does not fetch returned URLs;
- result URLs must be HTTP(S) when present;
- query/result/title/summary/metadata/TTL limits;
- provider iterables consumed only through the per-query limit plus one overflow sentinel;
- metadata must be JSON-serializable;
- malformed timestamps, provider drift, cache lineage drift and tampering fail closed;
- workspace validation is read-only; recovery writes are explicit.

2. Web-body download/materialization;
