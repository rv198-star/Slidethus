# Slidethus 可借鉴的能力

## 值得直接吸收的核心

### 1. PPT 是“内容工程 + 页面工程”，不是模板填充

Slidethus 的主流程应从用途、受众、演示场景和决策目标开始，而不是让模型看到标题就生成页数和版式。

### 2. 将“策划稿”设为正式中间产物

这是本素材最有价值的部分。建议 Slidethus 定义独立的 `Slide Plan`：

- 本页要回答的问题；
- 核心结论；
- 证据与数据；
- 信息层级；
- 页面构图；
- 视觉元素类型；
- 讲述者备注；
- 来源与可信度；
- 与前后页的叙事关系。

设计 Agent 不直接读取原始长文，而是读取经过审计的 Slide Plan。

### 3. 把大纲做成可重排的页面对象

“数字便利贴”可以进一步工程化为页面卡片对象，支持增删、重排、合并、拆分和局部重生成，而不是把大纲当一次性 Markdown。

### 4. 使用布局语法，而不是固定模板编号

Bento Grid 的价值不在“卡片风格”，而在于它把页面转成可描述、可约束、可验证的几何结构。Slidethus 可以扩展为布局 DSL：

- grid / split / stack / timeline / matrix / process / comparison / hero；
- 容器、间距、层级、对齐和视觉重心；
- 内容密度上限与最小字号；
- 图片、图表、文本和装饰元素的角色定义。

### 5. 先结构、后风格

先做灰模或策划稿，再应用主题 Token 和视觉资产，能显著降低模型同时处理内容、排版、审美和代码时的认知负担。

## 不应原样照搬的部分

- 不应把 Bento Grid 作为唯一布局；不同叙事任务需要流程图、时间线、矩阵、对比、地图、数据故事等不同语法。
- 不应把“一页一个整块 SVG”直接等同于“真正可编辑 PPT”；Slidethus 需要明确整页 SVG、可拆分 SVG、原生形状/文本框和混合模式的编辑等级。
- 不应把某一个模型或某一个搜索产品写死在架构中；模型、检索和渲染应是可替换服务。
- 不应只靠 Prompt 保证质量；需要 Schema、验证器、渲染预览、视觉审计与自动修复闭环。
